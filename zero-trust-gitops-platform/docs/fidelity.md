# Fidelity gaps

Where this repo's own build/dev environment can't faithfully reproduce what a real cloud
deployment or a contributor's machine can do, that gap is recorded here as it's discovered — not
glossed over. Started in Phase 1 (the sample workload's build); BRIEF.md's later phases (the local
`kind` demo, keyless signing, AWS identity) will add their own rows here as they land.

| Capability | Cloud / CI / contributor-machine implementation | This build environment | What is lost here |
|---|---|---|---|
| Container image build & run | `docker build` produces the real multi-stage image; `docker run` as UID 65532 serves `/healthz`; `docker run --entrypoint sh` fails for lack of a shell | No Docker daemon is reachable at all (`docker info` fails). `apps/demo-api/Dockerfile` is written and its two base images are digest-pinned via a live registry lookup (see `docs/versions.md`), but the image itself has never actually been built or run here | The three container-level checks BRIEF.md's Phase 1 gate asks for (non-root run, no-shell, and the image builds at all) are unverified in this environment. `make image` was run once to confirm it fails at exactly "cannot connect to the Docker daemon" and not from a bug in the Dockerfile or the `Makefile` invocation — that's the most this environment can prove |
| Build reproducibility | Two `docker build`s of the same commit produce the same image digest | Two `go build -trimpath` runs of the same commit, with the same `-ldflags`, produce byte-identical binaries (verified: matching `sha256sum`) | This proves the Go compiler output is deterministic for this program. It does not prove the *image* is reproducible — that also depends on deterministic layer/tar construction, which needs an actual `docker build` (BuildKit is deterministic for this Dockerfile's simple `COPY`-only layers in practice, but that's an expectation, not something checked here) |
| `terraform init` against the real provider registry | `terraform init` resolves `hashicorp/aws` from `registry.terraform.io` directly | `registry.terraform.io` is blocked from this sandbox (403; same for `registry.terraform.io/.well-known/terraform.json`, so even version discovery fails). Worked around by downloading `terraform-provider-aws` 6.64.0 directly from `releases.hashicorp.com` (reachable), verifying its SHA256 against HashiCorp's own `SHA256SUMS`, and pointing Terraform at it via a `filesystem_mirror` in a scratch `.terraformrc` (`TF_CLI_CONFIG_FILE`, never committed) | Every `terraform validate`/`plan`/`test`/`show -json` claimed elsewhere in this repo's history for Phase 2 was run for real against this mirror, not skipped — but only for `linux_amd64`, the one platform mirrored here |
| Cross-platform provider lock-file hashes | A normal `terraform init` against the real registry adds every requested platform's hash to `.terraform.lock.hcl` in one step | `terraform providers lock` itself refuses to run without reaching `registry.terraform.io` (it fetches origin-signed hashes even when a `filesystem_mirror` is configured for everything else), so `envs/dev/.terraform.lock.hcl` only carries a `linux_amd64` hash | A contributor on macOS/Windows, or CI on a different runner architecture, needs one ordinary `terraform init` (with real registry access) to add their platform's hash — it appends rather than replacing, so this isn't a conflict, just an incompleteness this sandbox couldn't fill in itself |
| Real AWS API calls during `plan` | A normal `terraform plan` may call `sts:GetCallerIdentity`, `ec2:DescribeAvailabilityZones`, etc. for `data` sources | No AWS account exists here, so every module was designed to need zero live AWS calls at plan time: `account_id` and `availability_zones` are plain input variables rather than `data "aws_caller_identity"`/`data "aws_availability_zones"`, and every `plan` run against these modules used the AWS provider's `skip_credentials_validation`/`skip_requesting_account_id`/`skip_region_validation`/`skip_metadata_api_check` flags with dummy static credentials | None, really — this is a design choice this repo would keep even with real AWS access (it makes the modules faster to plan and testable without credentials), documented here so the `skip_*` flags in ad-hoc smoke tests don't look like something hiding a real problem |
| `kubernetes_version` / EKS-addon versions | A real deployer checks AWS's current EKS-supported-Kubernetes-version list and each addon's compatible-version matrix before setting these | `docs.aws.amazon.com` and `aws.amazon.com` are both blocked here (403, org policy — not a registry-specific block), so that list was never reachable to check | `modules/eks`'s `kubernetes_version` variable has no default (the caller must supply a real, currently-supported version); `aws_eks_addon.pod_identity` pins no `addon_version` at all, letting AWS pick its own default rather than this repo guessing one. Both are deliberate "ask, don't guess" choices, not oversights — see Operating Rule 4 in `CLAUDE.md` |
| `checkov`'s guideline enrichment | `checkov` fetches extra guideline text per finding from `api0.prismacloud.io` | That host is blocked here (403) | Cosmetic only — `checkov`'s pass/fail verdicts and the finding descriptions it prints are unaffected; it just can't attach Bridgecrew's hosted guideline links. The scan itself (122 passed / 0 failed / 5 skipped as of Phase 2) is real |
| `kyverno test` for the 3 keyless `verifyImages` policies | `kyverno test`/admission verifies the Sigstore signature and attestations for real against Fulcio's current root-of-trust bundle and Rekor | `tuf-repo-cdn.sigstore.dev` (Fulcio's TUF root distribution point) is blocked here (403), confirmed directly via the actual error Kyverno returns. Every image reference — correctly signed or not — fails identically for this reason, so no fixture can demonstrate the "signed image is admitted" path offline. Each of `policies/tests/{verify-image-signature,verify-slsa-provenance,verify-sbom-attestation}/` ships a real `resource-fail.yaml` (an image with no digest at all, rejected before Kyverno would ever reach Fulcio — genuinely verified here) and a `resource-pass.yaml` plus a `NOTES.md` explaining why the pass case isn't asserted by `kyverno test` in this sandbox | The "signed image gets through" half of these three policies is proven for real in Phase 7's `demo/attack/01-unsigned-image.sh` / `04-wrong-signer-identity.sh` against a live cluster with real Sigstore access, and in CI's `e2e-kind.yml` (Phase 4+) — the layer that's actually supposed to verify a control depending on live cryptographic infrastructure, rather than a second offline test that would just assert this sandbox's network policy |
| `kyverno.io/v1 ClusterPolicy` API | Current Kyverno recommends the newer CEL-based `ValidatingPolicy`/`ImageValidatingPolicy`/etc. (`policies.kyverno.io`) CRDs | Every policy here still uses `kyverno.io/v1 ClusterPolicy` (with a deprecation warning on every `kyverno test`/`apply` run) | Deliberate, not an oversight: the CEL-based CRDs are a materially different policy language, still comparatively new, and BRIEF.md's own file tree, `kyverno-test.yaml` fixture format, and Chainsaw/Policy-Reporter integration all assume classic `ClusterPolicy` semantics. `ClusterPolicy` remains fully supported (only slated for eventual, not immediate, removal) — migrating is a real future improvement worth its own ADR, not something to do silently mid-policy-library |

Every row above will be checked for real in `.github/workflows/e2e-kind.yml` (a GitHub-hosted
runner, which does have Docker and reaches `registry.terraform.io` normally) once that workflow
exists (Phase 4+), and can be checked by any contributor with Docker and normal network access by
running `make image` / `terraform init` themselves.

## Phase 4 — CI/CD workflows (build, sign, attest, promote, policy gates)

| Capability | Cloud / CI / contributor-machine implementation | This build environment | What is lost here |
|---|---|---|---|
| Running the workflows themselves | A push/PR on GitHub actually schedules `build-sign-attest.yml`, `ci.yml`, `iac-scan.yml`, `policy-test.yml`, `codeql.yml`, `scorecard.yml`, `verify-no-secrets.yml` on GitHub-hosted runners, with real `id-token: write` OIDC tokens, a real GHCR registry, real Fulcio/Rekor access, and the GitHub API | This sandbox cannot trigger, watch, or inspect an actual GitHub Actions run (no `api.github.com` reach for Actions, and nothing here is a runner) | End-to-end proof that `build-sign-attest.yml` actually builds, signs keylessly, attests SBOM/SLSA-provenance, self-verifies, and opens a promotion PR — and that the other five workflows actually pass on their first real run — does not exist yet. What this sandbox *could* do for each workflow: statically validate the YAML (`actionlint`, plus `yamllint`/`check-yaml` via pre-commit — all real, all passing), verify every `uses:` action is pinned to a commit SHA that a `git ls-remote --tags` on the real upstream repo resolves to the stated version tag (done for every action in `docs/versions.md`'s GitHub Actions table), and manually trace each job's `needs:`/`permissions:`/`secrets:` wiring by reading it end to end. The actual first real run happens the first time this branch's commits reach GitHub, which is expected to surface at least minor issues (a wrong step output name, a shell quoting slip) no amount of static reading fully rules out — see the runbook note this phase adds under `docs/runbooks/` in a later phase for what to check first if that run fails |
| Registry for the demo image | BRIEF.md's original design pushes to AWS ECR, matching `infra/terraform/modules/ecr`'s access-controlled repository policy (OIDC-assumed `build` role pushes, a separate `pull_role_arn` pulls) | No AWS account backs this specific GitHub-hosted deployment (Phase 2's Terraform was never `apply`d — see above), so `build-sign-attest.yml` pushes to `ghcr.io/beniaxcode/yahia-benabbou-portfolio/demo-api` instead, authenticating with the ambient `GITHUB_TOKEN` (itself OIDC-derived, satisfying C1 with zero added secrets) rather than an AWS-OIDC-assumed role | The identity mechanism this repo demonstrates (short-lived, workflow-scoped credentials, never a static key) is the same either way — only the registry vendor differs. `infra/terraform/modules/ecr` stays the documented production path: a real deployment onto the Terraform in this repo would point `REGISTRY`/`IMAGE_NAME` at ECR and swap the `docker/login-action` step for `aws-actions/configure-aws-credentials` (OIDC) + `aws ecr get-login-password`, with no other change to the sign/attest/verify logic. `policies/supply-chain/allowed-registries.yaml` and the three `verifyImages` policies already accept both patterns for exactly this reason |
| gitleaks custom rule for "no GitHub Actions secret besides `GITHUB_TOKEN`" | N/A — this is a repo-authoring finding, not an environment gap | A custom `[[rules]]` entry was first written to have gitleaks itself flag any `${{ secrets.X }}`/`secrets['X']` reference where `X != GITHUB_TOKEN`. Testing it against a deliberately-planted violation (`${{ secrets.MY_CUSTOM_PAT }}`) showed it never fires while `[extend] useDefault = true`: gitleaks's own default config (`config/gitleaks.toml`) ships a global allowlist regex, `^\$\{\{[ \t]*(?:(?:env\|github\|secrets\|vars)(?:\.[A-Za-z]\w+)+[\w "'&./=\|]*)[ \t]*}}$`, that treats *any* `${{ secrets.* }}` expression as a template placeholder rather than a leaked value — correct for gitleaks's actual job (finding literal secret material), but it unconditionally swallows a policy check like this one | `.gitleaks.toml` was corrected to drop the rule rather than fight the tool's own design (confirmed by direct testing, not assumed). C1 is enforced instead by `tools/check-no-secrets.sh` — a small bespoke script, not a secret scanner — wired into both pre-commit and `.github/workflows/verify-no-secrets.yml`; that script was itself testing-corrected once, after its first version's regex matched the substring `"secrets.sh"` inside `check-no-secrets.sh`'s own filename in `verify-no-secrets.yml`'s prose and `run:` line, and a second time to add a documented exception for `slsa-provenance.yml`'s legitimate forwarding of its own declared `registry-password` workflow_call secret input (always filled with `secrets.GITHUB_TOKEN` by its one caller). Both the false-positive fix and the gitleaks-rule removal were verified by re-planting the same deliberate violation and confirming the check still fails on it before being restored |

Both of Phase 4's mechanical gaps above (no live Actions run, GHCR-not-ECR) are structural to this
sandbox and this specific deployment rather than bugs; they narrow, in the same honest way as every
row before them, exactly what "the pre-commit and static-analysis gates in this repo pass" does and
does not prove on its own.

## Phase 5 — Argo CD and the GitOps layer

| Capability | Cloud / CI / contributor-machine implementation | This build environment | What is lost here |
|---|---|---|---|
| The Phase 5 gate itself ("on kind, `make demo` reaches all Applications Synced + Healthy; a manual `kubectl edit deploy` is reverted by self-heal, asserted by a test") | A machine with Docker brings up a real `kind` cluster, installs Argo CD, lets it reconcile `gitops/`, and can literally run the self-heal assertion | No Docker daemon is reachable here (the same constraint recorded against Phase 1's container-build gate), so there is no cluster to bring up and no Argo CD controller to reconcile anything | This gate is unverified in this environment, full stop — not approximated, not partially checked. What *is* checked for real here, and is exactly what a live Argo CD would also do before ever touching the API server: every `gitops/apps/demo-api/{base,overlays/*}` kustomization builds with real `kustomize build` (all three overlays render, prod correctly picks up its extra `PodDisruptionBudget`), and the rendered output of all three passes this repo's own shift-left `kyverno apply policies/*/` check clean (25 pass / 0 fail / 2 skip — the 2 skips are the init-container digest rule, correctly inapplicable since neither manifest has an initContainer). Every `gitops/platform/*/application.yaml` and the two `gitops/bootstrap/*.yaml` root Applications are valid YAML matching the Argo CD `argoproj.io/v1alpha1` CRD schema as documented, but were never submitted to a real API server, so a schema mistake this sandbox's own tooling doesn't catch (this repo has no local copy of Argo CD's CRD OpenAPI schema to validate against) would only surface on a live cluster. `demo/kind-cluster.yaml` / `demo/up.sh` / `demo/down.sh` — the scripts that would actually run this gate — are deliberately not written in this phase; they land once there is more for them to bring up (Phase 6/7), and will be the first place this whole gap actually closes, on a machine with Docker |
| The GitOps bootstrap digest | A real first deployment has *some* real, already-signed image to point the very first `Sync` at | `gitops/apps/demo-api/base/deployment.yaml`'s `images:` transformer (in `kustomization.yaml`) pins a syntactically-valid but entirely fake digest (`sha256:000...0`) — chosen deliberately obviously-fake rather than a plausible-looking one, so it can never be mistaken for a real value. It has never been built, signed, or pushed anywhere | Kyverno's three `verifyImages` policies (already known from Phase 3 to be unable to reach Fulcio's TUF root from here) would — and, on a real GitHub-hosted runner with real Sigstore access, *will* — correctly refuse to verify this placeholder, since it was never actually signed. This is expected and correct, not a bug: the very first real run of `build-sign-attest.yml` on this branch, once it reaches GitHub, builds and signs a real image and opens the first real `promote.yml` PR for each environment; only once that PR merges does each overlay's digest stop being a placeholder. Until then, `ci.yml`'s shift-left-admission-preview job rendering these overlays will legitimately show a `verifyImages` failure for this reason — a real, correctly-firing control, not a false positive, and not something to suppress to make an early CI run look green |
| Argo CD OIDC SSO / local-only login fallback | A real OIDC provider is configured in `argocd-cm`; a break-glass local login exists for cases where OIDC is unreachable | `gitops/platform/argocd/values.yaml`'s `configs.cm."oidc.config"` is an illustrative example pointed at a non-existent issuer, and the admin account is disabled (`admin.enabled: "false"`) with no checked-in local credential — deliberately, since a checked-in login credential of any kind is exactly the kind of thing this repo's threat model treats as a static credential to avoid | Nobody has ever actually logged into an Argo CD instance built from these values, here or anywhere — there is no cluster. The documented local-only fallback (an `argocd admin dashboard` port-forward, or `kubectl exec` into a controller pod) is asserted from Argo CD's own documented behavior, not exercised |
| Argo CD / Kyverno / ESO / Policy Reporter / metrics-server Helm chart pins | `helm repo add` + `helm search repo` (or the packaged chart repo's `index.yaml`) resolve the current chart version directly | `argoproj.github.io`, `kyverno.github.io` (×2), `charts.external-secrets.io`, and `kubernetes-sigs.github.io` are all unreachable from this sandbox (a proxy-level connection rejection, distinct from the `registry.terraform.io` 403 pattern seen in Phase 2) | Worked around the same way Phase 4's GitHub Action SHAs were: `git ls-remote --tags` against each project's real source repository (not the packaged chart repo) finds the newest chart-release tag, and `raw.githubusercontent.com` fetches that tag's actual `Chart.yaml` for its real `version`/`appVersion` fields — see `docs/versions.md`'s Helm charts table for the full method and a discovered correction (Policy Reporter and External Secrets Operator's `go list -m`-resolved versions in the "Platform / cluster tooling" table were stale, for the same `go.mod`-doesn't-track-releases reason as `hashicorp/aws` in Phase 2) |

Two real, in-repo bugs were also found and fixed while gating this phase, neither an environment
gap: `kyverno apply <dir>` does not recurse into a directory's own subdirectories (a bare
`.../policies/` — as `ci.yml`'s shift-left step was written — loads zero policies silently; fixed
to `.../policies/*/`, confirmed by testing to actually load and evaluate all of them), and
`policies/governance/require-probes.yaml` needed `pod-policies.kyverno.io/autogen-controllers:
DaemonSet,Deployment,StatefulSet` added so Kyverno's autogen machinery stops requiring a
liveness/readiness probe on the new PreSync verification `Job` (a run-to-completion workload, for
which that requirement is meaningless) — discovered by actually rendering
`gitops/apps/demo-api/base` and running the shift-left check against it, not by inspection.
`policies/supply-chain/allowed-registries.yaml` also gained one narrow, explicitly digest-pinned
exception for the upstream `gcr.io/projectsigstore/cosign` image that hook Job runs, rather than
widening the rule to any third-party registry.

## Phase 6 — runtime zero-trust posture

| Capability | Cloud / CI / contributor-machine implementation | This build environment | What is lost here |
|---|---|---|---|
| NetworkPolicy enforcement on `make demo`'s cluster | A real EKS cluster's CNI (the AWS VPC CNI, or Calico/Cilium alongside it) enforces `NetworkPolicy` objects for real | Plain `kind create cluster` uses kindnet, which does **not** enforce `NetworkPolicy` at all — every default-deny object `policies/generate/default-deny-networkpolicy.yaml` generates, and every explicit allow this phase adds, would be silently inert. `demo/kind-cluster.yaml` sets `networking.disableDefaultCNI: true` specifically so `demo/up.sh` can install Calico (v3.32.2 — see docs/versions.md) instead, which does enforce them | Confirmed by reading kind's and Calico's own documentation and cross-checking `disableDefaultCNI`'s real effect against `kind-cluster.yaml`'s syntax — never exercised against an actual cluster, since this sandbox has no Docker daemon (the same gap recorded against every prior phase's cluster-dependent claims). This is also the most important line in `docs/fidelity.md` for anyone about to trust Phase 7's `demo/attack/06-exfiltrate-node-role.sh`: without Calico actually running, that scenario's "NetworkPolicy blocks it" half would pass for the wrong reason (nothing enforcing anything) rather than the right one |
| C9 applying to *every* namespace, not just app namespaces | A real deployment either scopes `default-deny-networkpolicy.yaml`'s exclusion list to cover every namespace that needs different treatment, or gives each platform component's own NetworkPolicy real per-component review | `policies/generate/default-deny-networkpolicy.yaml` excludes only the four built-in system namespaces, so `argocd`, `kyverno`, `external-secrets`, `policy-reporter`, and the new `platform-verification` all get the same generated deny-all as `demo-api-{dev,staging,prod}`. Each platform namespace's `gitops/platform/*/manifests/networkpolicy.yaml` adds the same functional baseline (same-namespace traffic, DNS, HTTPS egress) rather than a fully least-privileged, per-component policy | This baseline is deliberately not least-privileged: it does not enumerate Argo CD's internal server↔repo-server↔redis↔application-controller ports, ESO's exact AWS Secrets Manager endpoint pattern, or Kyverno's specific webhook ports. Getting those exactly right without a live cluster to catch a wrong guess risks shipping a NetworkPolicy that *looks* more precise but silently breaks the platform — worse than the honest, coarser baseline here. The kubelet/API-server-originated ingress traffic (health probes, the admission webhook call) is flagged in each of these files as the same CNI-dependent, node-originated traffic pattern already noted for `demo-api`'s own NetworkPolicy — whether it needs a NetworkPolicy allowance at all depends on the CNI, not on anything this repo's manifests can decide |
| The continuous-verification CronJob's own container image | A real production deployment would build a small purpose-built image (kubectl + cosign, nothing else) via this repo's own signed-build pipeline | No Docker daemon exists here to build one, so `gitops/platform/verification/cronjob.yaml` instead pairs the official, distroless (confirmed via its real `.ko.yaml` and image config — not assumed) `cosign` image with `bitnami/kubectl`, fetching a real, checksum-verified `cosign` release binary at runtime rather than trying to copy one out of a shell-less distroless image (confirmed impossible: distroless has no `cp`, no shell, nothing but the one static binary at its `Entrypoint`) | Functionally complete and checksum-verified at every step, but re-downloads a ~130MB binary on every 15-minute run — a real inefficiency a purpose-built image would remove, once this repo's build environment can actually build one. `bitnami/kubectl`'s own baked-in `kubectl` version could not be cross-checked (Docker Hub's blob CDN redirect is blocked here, same gap as the digest itself — see docs/versions.md) |
| ESO `ClusterSecretStore` backends (both) | A real deployment provisions Secrets Manager entries via Terraform (`infra/terraform/modules/secrets`, no `aws_secretsmanager_secret_version` per C7) and lets ESO read them at runtime via Pod Identity | Neither `aws-secrets-manager` nor `local-demo` (the kind-only substitute, backed by a plain in-cluster Secret `demo/up.sh` seeds) has ever been reconciled by a running ESO — there is no cluster. Both are asserted correct against ESO's documented CRD schema, not exercised | The two backends intentionally use incompatible key-naming conventions (AWS Secrets Manager's path-style `zero-trust-gitops-platform/demo-api/demo-secret` is not a legal Kubernetes object name), so `gitops/apps/demo-api/base/externalsecret.yaml`'s default `remoteRef.key` (a plain, k8s-legal name) only works against `local-demo`; the prod overlay patches both `secretStoreRef.name` *and* `remoteRef.key` together when switching to the real backend — a mismatch here would silently resolve to "secret not found" on a real cluster, not a build-time error, so this was checked by rendering both overlays and diffing the patched output, not by inspection alone |
| Falco / Tetragon (BRIEF's "optional, clearly marked module") | A real deployment installing one gets eBPF-based runtime detection of the exact behaviors Phase 7's attack scenarios attempt | Not implemented. Given the module is explicitly optional in BRIEF.md itself, and neither tool can be meaningfully evaluated without a real running kernel/cluster to observe (unlike everything else in `gitops/platform/`, which at least renders and validates offline), building it out now would produce untested Helm values with no way to catch a wrong one — the same reasoning already applied to not over-specifying the platform NetworkPolicies above. Deferred to an ADR in Phase 8 (`docs/adr/`) that records the decision and its reasoning explicitly, rather than a half-wired module nobody asked for at this fidelity level |

Two real, in-repo issues were found and fixed while gating this phase: the continuous-verify
CronJob's own image (`docker.io/bitnami/kubectl`) needed the same kind of narrow, digest-pinned
`allowed-registries.yaml` exception the cosign image already had — caught by actually running the
shift-left check against it, not by inspection; and `demo/up.sh`'s first draft tried to
`kubectl apply` the `gitops/bootstrap/` `Application` objects before Argo CD's own CRDs existed —
the classic self-management bootstrap chicken-and-egg, fixed by adding a one-time imperative
install of Argo CD's stock manifest first, exactly as Argo CD's own documentation describes for
this pattern.
