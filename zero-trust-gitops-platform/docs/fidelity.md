# Fidelity gaps

Where this repo's own build/dev environment can't faithfully reproduce what a real cloud
deployment or a contributor's machine can do, that gap is recorded here as it's discovered — not
glossed over. Started in Phase 1 (the sample workload's build); BRIEF.md's later phases (the local
`kind` demo, keyless signing, AWS identity) will add their own rows here as they land.

| Capability | Cloud / CI / contributor-machine implementation | This build environment | What is lost here |
|---|---|---|---|
| Container image build & run | `docker build` produces the real multi-stage image; `docker run` as UID 65532 serves `/healthz`; `docker run --entrypoint sh` fails for lack of a shell | No Docker daemon is reachable at all (`docker info` fails). `apps/demo-api/Dockerfile` is written and its two base images are digest-pinned via a live registry lookup (see `docs/versions.md`), but the image itself has never actually been built or run here | The three container-level checks BRIEF.md's Phase 1 gate asks for (non-root run, no-shell, and the image builds at all) are unverified in this environment. `make image` was run once to confirm it fails at exactly "cannot connect to the Docker daemon" and not from a bug in the Dockerfile or the `Makefile` invocation — that's the most this environment can prove |
| Build reproducibility | Two `docker build`s of the same commit produce the same image digest | Two `go build -trimpath` runs of the same commit, with the same `-ldflags`, produce byte-identical binaries (verified: matching `sha256sum`) | This proves the Go compiler output is deterministic for this program. It does not prove the *image* is reproducible — that also depends on deterministic layer/tar construction, which needs an actual `docker build` (BuildKit is deterministic for this Dockerfile's simple `COPY`-only layers in practice, but that's an expectation, not something checked here) |
| `terraform init` against the real provider registry | `terraform init` resolves `hashicorp/aws` from `registry.terraform.io` directly | `registry.terraform.io` is blocked from this sandbox (403; same for `registry.terraform.io/.well-known/terraform.json`, so even version discovery fails). Worked around by downloading `terraform-provider-aws` 6.64.0 directly from `releases.hashicorp.com` (reachable), verifying its SHA256 against HashiCorp's own `SHA256SUMS`, and pointing Terraform at it via a `filesystem_mirror` in a scratch `.terraformrc` (`TF_CLI_CONFIG_FILE`, never committed) | Every `terraform validate`/`plan`/`test`/`show -json` claimed elsewhere in this repo's history for Phase 2 was run for real against this mirror, not skipped — but only for `linux_amd64`, the one platform mirrored here |
| Cross-platform provider lock-file hashes | A normal `terraform init` against the real registry adds every requested platform's hash to `.terraform.lock.hcl` in one step | `terraform providers lock` itself refuses to run without reaching `registry.terraform.io` (it fetches origin-signed hashes even when a `filesystem_mirror` is configured for everything else), so `envs/dev/.terraform.lock.hcl` only carries a `linux_amd64` hash | A contributor on macOS/Windows, or CI on a different runner architecture, needs one ordinary `terraform init` (with real registry access) to add their platform's hash — it appends rather than replacing, so this isn't a conflict, just an incompleteness this sandbox couldn't fill in itself |
| Real AWS API calls during `plan` | A normal `terraform plan` may call `sts:GetCallerIdentity`, `ec2:DescribeAvailabilityZones`, etc. for `data` sources | No AWS account exists here, so every module was designed to need zero live AWS calls at plan time: `account_id` and `availability_zones` are plain input variables rather than `data "aws_caller_identity"`/`data "aws_availability_zones"`, and every `plan` run against these modules used the AWS provider's `skip_credentials_validation`/`skip_requesting_account_id`/`skip_region_validation`/`skip_metadata_api_check` flags with dummy static credentials | None, really — this is a design choice this repo would keep even with real AWS access (it makes the modules faster to plan and testable without credentials), documented here so the `skip_*` flags in ad-hoc smoke tests don't look like something hiding a real problem |
| `kubernetes_version` / EKS-addon versions | A real deployer checks AWS's current EKS-supported-Kubernetes-version list and each addon's compatible-version matrix before setting these | `docs.aws.amazon.com` and `aws.amazon.com` are both blocked here (403, org policy — not a registry-specific block), so that list was never reachable to check | `modules/eks`'s `kubernetes_version` variable has no default (the caller must supply a real, currently-supported version); `aws_eks_addon.pod_identity` pins no `addon_version` at all, letting AWS pick its own default rather than this repo guessing one. Both are deliberate "ask, don't guess" choices, not oversights — see Operating Rule 4 in `CLAUDE.md` |
| `checkov`'s guideline enrichment | `checkov` fetches extra guideline text per finding from `api0.prismacloud.io` | That host is blocked here (403) | Cosmetic only — `checkov`'s pass/fail verdicts and the finding descriptions it prints are unaffected; it just can't attach Bridgecrew's hosted guideline links. The scan itself (122 passed / 0 failed / 5 skipped as of Phase 2) is real |
| `kyverno test` for the 3 keyless `verifyImages` policies | `kyverno test`/admission verifies the Sigstore signature and attestations for real against Fulcio's current root-of-trust bundle and Rekor | `tuf-repo-cdn.sigstore.dev` (Fulcio's TUF root distribution point) is blocked here (403), confirmed directly via the actual error Kyverno returns. Every image reference — correctly signed or not — fails identically for this reason, so no fixture can demonstrate the "signed image is admitted" path offline. Each of `policies/tests/{verify-image-signature,verify-slsa-provenance,verify-sbom-attestation}/` ships a real `resource-fail.yaml` (an image with no digest at all, rejected before Kyverno would ever reach Fulcio — genuinely verified here) and a `resource-pass.yaml` plus a `NOTES.md` explaining why the pass case isn't asserted by `kyverno test` in this sandbox | The "signed image gets through" half of these three policies is proven for real in Phase 7's `demo/attack/01-unsigned-image.sh` / `04-wrong-signer-identity.sh` against a live cluster with real Sigstore access, and in CI's `e2e-kind.yml` (Phase 4+) — the layer that's actually supposed to verify a control depending on live cryptographic infrastructure, rather than a second offline test that would just assert this sandbox's network policy |
| `kyverno.io/v1 ClusterPolicy` API | Current Kyverno recommends the newer CEL-based `ValidatingPolicy`/`ImageValidatingPolicy`/etc. (`policies.kyverno.io`) CRDs | Every policy here still uses `kyverno.io/v1 ClusterPolicy` (with a deprecation warning on every `kyverno test`/`apply` run) | Deliberate, not an oversight: the CEL-based CRDs are a materially different policy language, still comparatively new, and BRIEF.md's own file tree, `kyverno-test.yaml` fixture format, and Chainsaw/Policy-Reporter integration all assume classic `ClusterPolicy` semantics. `ClusterPolicy` remains fully supported (only slated for eventual, not immediate, removal) — migrating is a real future improvement worth its own ADR, not something to do silently mid-policy-library |

Every row above will be checked for real in `.github/workflows/e2e-kind.yml` (a GitHub-hosted
runner, which does have Docker and reaches `registry.terraform.io` normally) once that workflow
exists (Phase 4+), and can be checked by any contributor with Docker and normal network access by
running `make image` / `terraform init` themselves.
